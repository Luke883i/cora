## GitHub-native workflow
1. Create a topic branch at an exact `main` SHA. Author atomic semantic commits with source changes, independent negative tests, build/verification changes, documentation and DoD. The branch is not an approval.
2. Open a **Draft Pull Request** targeting `main`. Include exact base and head SHA, changelog, threat/compatibility impact, explicit open obligations and evidence links. Use GitHub **Checks** and Actions workflow runs from that exact HEAD, never an author-provided screenshot or unverifiable hash.
3. Run `python -m unittest discover -s tests -v`, `python tools/verify_repository_contract.py --repo .`, `python tools/verify_artifact_roles.py --repo .`, `python tools/verify_release_readiness.py --repo .` and CORA-on-CORA read-only `process-run` + `verify-process`. Build/install wheel and sdist through the existing pinned release-candidate workflow. Retain exact-artifact SHA-256 and Python 3.11/3.13 test evidence.
4. An **administrator** must separately verify that protected `main` requires trusted checks and a non-author reviewer. Check active branch rules; CODEOWNERS text and CI-green detection do not establish enforcement. Any unavailable admin evidence means **BLOCKED_EXTERNAL**.
5. After independent review and all DoD obligations, the authorized maintainer merges through GitHub. Re-run post-merge verification on exact merge SHA; confirm all required checks. An approved human **release manager** may then create a protected, version-matched tag (e.g. `v1.0.0a4`), and a GitHub **Release** marked **pre-release** with release notes, wheel/sdist, hashes and source/build provenance when verified. The tag and assets must refer to the reviewed commit. Neither the PR nor an alpha version implies publication.
6. Record post-release issues/monitoring, rollback and consumer impact in GitHub Issues/PRs and document owners. Do not infer deployment SLOs or incident-free operation without a monitored system.

## Reproducibility and downgrade path
A passing source verifier is a bounded metadata result, not an access-control assertion. A failed or unavailable check leaves the PR Draft and the release unpublished. Existing build scripts produce candidate artifacts but do not create GitHub Releases, publish to PyPI or sign provenance. This release procedure itself cannot configure GitHub branch protections; the first trusted bootstrap must be approved independently.

**Source and host inspection (read-only):** After an authorized checkout of the exact candidate commit, rerun `python -m unittest discover -s tests -q` on Python 3.11 and 3.13. Verify source readiness using `python tools/verify_release_readiness.py --repo . --output /tmp/cora-release-source.json`. When a GitHub read-only token is available, run `GITHUB_TOKEN=... python tools/verify_release_readiness.py --repo . --observe-host --host-repository Luke883i/cora --host-commit "$(git rev-parse HEAD)" --host-output /tmp/cora-host.json` (do not put tokens in logs or artifacts). The host check reads the current GitHub main branch, rulesets and release-tag endpoint. In GitHub Actions, the authenticated live observer runs **only on push to main**, never on pull requests: untrusted PR code must not receive even a read-only private-repository token. Pull requests execute deterministic synthetic/physical falsifiers without the live token. It records `BLOCKED_EXTERNAL` regardless of observed hosting configuration, because review independence, approval, signed provenance, asset/tag parity and real pilot remain distinct decisions. A private repository's 403 ruleset response is **unavailable evidence**, not evidence of required checks being active.

**Artifact qualification after gates:** Run the existing `CI | CORA release candidate verification` on the exact reviewed SHA, obtain its named review-only wheel and sdist, verify Python 3.11/3.13 candidate runs, source parity, two-build reproducibility, archive safety and independent fixture installation. Check the actual built wheel/sdist SHA-256 against those intended for publication. Obtain and independently review release provenance, CI final-SHA results, source/test qualifications, owner sign-off, and genuine user/third-party pilot evidence. None can be replaced by the million-case deterministic finite-model stress.

**Explicit publication by the authorized operator only:** From a clean, reviewed checkout of the exact approved commit, verify the package metadata version `1.0.0a4`; create and push a protected annotated tag `v1.0.0a4` naming exactly that commit. Verify the remote tag target. Then in GitHub Releases select **Draft a new release**, use that existing tag, tick **This is a pre-release**, attach only the reviewed wheel/sdist plus SHA-256 and provenance/verification reports, include release notes and external limitations, and publish after release-manager approval. The command-line alternative, **after all the above gates**, is `gh release create v1.0.0a4 dist/cora_audit-1.0.0a4-py3-none-any.whl dist/cora_audit-1.0.0a4.tar.gz --verify-tag --prerelease --title "CORA 1.0.0a4 (alpha)" --notes-file RELEASE_NOTES.md` (with real reviewed artifact paths). ## PR39 — independent product acceptance protocol (external operator work)

**Separation of duties:** The implementer must not certify their own software. Assign a reviewer independent of the PR author, a host administrator authorized to inspect effective protected branch settings, a runtime host operator and an independent usability observer. Each outside record must carry commit, target version, environment, timestamp, role, reviewer, expected outcome, actual outcome and secure evidence location. Authenticate those identities outside the candidate repository. A self-issued file, a CI badge and a digest are insufficient.

**Behavioral oracle (G_BEHAVIOR):** Execute tools/independent_git_oracle.py in a clean environment and retain its native-Git comparison. Independently select at least two real, actively maintained repositories of different profiles. A distinct accountable test owner must pre-register expected results from a separately implemented or separately reviewed oracle, exact target commits, expected unknowns and thresholds. Record false negatives and false positives; require zero critical false PASS. Two synthetic Git fixtures cannot close this external requirement.

**Usability (G_USABILITY):** Recruit at least eight actual participants from the first-time developer and independent assurance reviewer personas, spanning at least two real repositories. Pre-register at least three tasks per participant: run comprehensive One-Run; find a commit, test and evidence source; explain why BLOCKED or NOT_RUN is not product PASS. Time limit: twenty minutes per participant. Require at least 80% task completion and zero critical proof-level misclassifications. Use pseudonyms and do not commit personal data or recordings. The study packet analyzer checks numbers only: it cannot authenticate participants, consent, observer or results.

**Isolation (G_ISOLATION):** Before running hostile code, have an independent host operator verify a disposable isolated VM/container environment with immutable image, non-root user, no network access or secrets, read-only source and root, capabilities removed, security policy, CPU/memory/PID/time limits and independently monitored cleanup. Test denied network/filesystem access, bounded resources and effective termination after timeout. Record host/daemon version, effective settings and observation from outside the tested process. The existing Docker CLI flags and mocked tests are source-level design evidence, not host safety proof. In particular, a Docker CLI timeout does not prove container termination.

**Governance (G_GOVERNANCE):** Obtain host-authorized readback of effective main branch protections and applicable rulesets, check required status names against exact HEAD CI, prove reviewer independence and bypass restrictions, and conduct an authorized release/rollback drill. A read-only GitHub 403 response is a lack of observation, not evidence that controls are absent. A source YAML file or a green CI cannot verify effective branch protection. Release must remain an independently accountable human decision.

**Noncompensatory product DoD:** Accept only when all four gates have separately attributable, independently verified and fresh evidence. If any identity, maintained target, live study, runtime host policy, rule protection or rollback cannot be verified, product status remains BLOCKED_EXTERNAL. No source-local test, mocked operator, self-issued review or generated report may authorize merging, shipping or deletion.
