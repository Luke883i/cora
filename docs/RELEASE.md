# CORA governed prerelease procedure (GitHub and Python distribution)

Status: **staged, not published**. Product name: CORA — Continuous Ontological Repository Assurance. Package: `cora-audit`; software: `cora-engine` and `cora-release-verification`; repository: `Luke883i/cora`. Current repository version: `1.0.0a4` (PEP 440 *alpha*). PR-20 is merged into source, but there is no independently authenticated public release or published stable 1.0.0. The original PR-15 introduced this version identity; merging later PRs does not attest release readiness.

## GitHub-native workflow
1. Create a topic branch at an exact `main` SHA. Author atomic semantic commits with source changes, independent negative tests, build/verification changes, documentation and DoD. The branch is not an approval.
2. Open a **Draft Pull Request** targeting `main`. Include exact base and head SHA, changelog, threat/compatibility impact, explicit open obligations and evidence links. Use GitHub **Checks** and Actions workflow runs from that exact HEAD, never an author-provided screenshot or unverifiable hash.
3. Run `python -m unittest discover -s tests -v`, `python tools/verify_repository_contract.py --repo .`, `python tools/verify_artifact_roles.py --repo .`, `python tools/verify_release_readiness.py --repo .` and CORA-on-CORA read-only `process-run` + `verify-process`. Build/install wheel and sdist through the existing pinned release-candidate workflow. Retain exact-artifact SHA-256 and Python 3.11/3.13 test evidence.
4. An **administrator** must separately verify that protected `main` requires trusted checks and a non-author reviewer. Check active branch rules; CODEOWNERS text and CI-green detection do not establish enforcement. Any unavailable admin evidence means **BLOCKED_EXTERNAL**.
5. After independent review and all DoD obligations, the authorized maintainer merges through GitHub. Re-run post-merge verification on exact merge SHA; confirm all required checks. An approved human **release manager** may then create a protected, version-matched tag (e.g. `v1.0.0a4`), and a GitHub **Release** marked **pre-release** with release notes, wheel/sdist, hashes and source/build provenance when verified. The tag and assets must refer to the reviewed commit. Neither the PR nor an alpha version implies publication.
6. Record post-release issues/monitoring, rollback and consumer impact in GitHub Issues/PRs and document owners. Do not infer deployment SLOs or incident-free operation without a monitored system.

## Reproducibility and downgrade path
A passing source verifier is a bounded metadata result, not an access-control assertion. A failed or unavailable check leaves the PR Draft and the release unpublished. Existing build scripts produce candidate artifacts but do not create GitHub Releases, publish to PyPI or sign provenance. This release procedure itself cannot configure GitHub branch protections; the first trusted bootstrap must be approved independently.

## PR32 — exact-SHA GitHub pre-release procedure and real host evidence

The existing candidate builders create a **wheel** and **sdist**; they do not publish. Publishing an experimental `v1.0.0a4` GitHub Pre-release requires an authorized human release manager, named non-author review, validated commit and verified provenance. CORA cannot set host branch protection, authenticate a human, sign an artifact on behalf of a release manager, or declare a production release. Treat a failed diagnostic as an open blocker even when the primary CI matrix is green.

**Source and host inspection (read-only):** After an authorized checkout of the exact candidate commit, rerun `python -m unittest discover -s tests -q` on Python 3.11 and 3.13. Verify source readiness using `python tools/verify_release_readiness.py --repo . --output /tmp/cora-release-source.json`. When a GitHub read-only token is available, run `GITHUB_TOKEN=... python tools/verify_release_readiness.py --repo . --observe-host --host-repository Luke883i/cora --host-commit "$(git rev-parse HEAD)" --host-output /tmp/cora-host.json` (do not put tokens in logs or artifacts). The host check reads the current GitHub main branch, rulesets and release-tag endpoint. In GitHub Actions, the authenticated live observer runs **only on push to main**, never on pull requests: untrusted PR code must not receive even a read-only private-repository token. Pull requests execute deterministic synthetic/physical falsifiers without the live token. It records `BLOCKED_EXTERNAL` regardless of observed hosting configuration, because review independence, approval, signed provenance, asset/tag parity and real pilot remain distinct decisions. A private repository's 403 ruleset response is **unavailable evidence**, not evidence of required checks being active.

**Artifact qualification after gates:** Run the existing `CI | CORA release candidate verification` on the exact reviewed SHA, obtain its named review-only wheel and sdist, verify Python 3.11/3.13 candidate runs, source parity, two-build reproducibility, archive safety and independent fixture installation. Check the actual built wheel/sdist SHA-256 against those intended for publication. Obtain and independently review release provenance, CI final-SHA results, source/test qualifications, owner sign-off, and genuine user/third-party pilot evidence. None can be replaced by the million-case deterministic finite-model stress.

**Explicit publication by the authorized operator only:** From a clean, reviewed checkout of the exact approved commit, verify the package metadata version `1.0.0a4`; create and push a protected annotated tag `v1.0.0a4` naming exactly that commit. Verify the remote tag target. Then in GitHub Releases select **Draft a new release**, use that existing tag, tick **This is a pre-release**, attach only the reviewed wheel/sdist plus SHA-256 and provenance/verification reports, include release notes and external limitations, and publish after release-manager approval. The command-line alternative, **after all the above gates**, is `gh release create v1.0.0a4 dist/cora_audit-1.0.0a4-py3-none-any.whl dist/cora_audit-1.0.0a4.tar.gz --verify-tag --prerelease --title "CORA 1.0.0a4 (alpha)" --notes-file RELEASE_NOTES.md` (with real reviewed artifact paths). GitHub Actions in this repository have read-only permissions and intentionally do **not** auto-create tags or releases.

**Current blocking facts as of 5 November 2026:** The read-only GitHub branch observation returned `protected=false` and no enforced required checks, and a merged-main Python 3.13 diagnostic failed while an equivalent-tree PR head passed. The PR32 reticulum uses original Git source and live host evidence to preserve these failures, not to promote release readiness. GitHub release publication remains operator-controlled and blocked until separately authorized.

## PR34 — release candidate manifest and release-manager checklist

The `CI | CORA release candidate verification` job now checks out the **actual PR HEAD** (not GitHub's ephemeral synthetic merge commit), verifies the original Git object and clean tracked source, builds wheel/sdist twice, checks archive safety, compares payload to original source, installs wheel and sdist into separate local venv fixtures, and produces the following **review-only artifacts** for each Python version: `candidate-receipt.json`, `release-source.json`, `SHA256SUMS`, `RELEASE_NOTES_REVIEW.txt`, verified wheel/sdist, validation reports and the experimental bundle. Source identity and binary SHA-256 are automatically reconciled. This is a candidate, not a supplier-signed provenance attestation.

**Measurable prepublication checklist (noncompensatory; all required):**

- [ ] Exact intended final `main` commit and tag target match the previously qualified source and binaries.
- [ ] **All** required CI on the actual final main commit succeeds, including independently observed PR25/PR26 repeats with 0 failed attempts on Python 3.11/3.13 and identified cause or explicit open debt for historical divergence.
- [ ] `SHA256SUMS` matches **the actual wheel and sdist to be uploaded**, with install and source parity reports from the same commit.
- [ ] GitHub branch protection and required checks demonstrably enforce the approved branch rules. Repository source declarations are not sufficient.
- [ ] Authenticated independent non-author reviewer approves the actual release change and release manager explicitly authorizes publication.
- [ ] Provenance/signatures are independently validated, external pilot and rollback owner are recorded, and release notes clearly mark alpha limitations.
- [ ] `v1.0.0a4` is created and verified as an annotated tag pointing to the approved commit, **after** all above conditions.
- [ ] Only then publish the GitHub Release as a **pre-release** using the verified assets; record published tag, SHA, artifact digests and operator.

**Current classification:** `BLOCKED_EXTERNAL`. A passing PR34 manifest cannot clear hosted governance, independent release consent, provenance signing, real target acceptance or past unexplained Git-test failures. Do not auto-publish or use unchecked CI artifacts as evidence of a public release.
